### ديون فنية موثقة (مؤجلة للمرحلة الاستراتيجية عن قصد)

هذه إصلاحات إسعافية حذرة الحدّ الأدنى. الحلول البنيوية الصحيحة المؤجلة:

1. **معرّف صف فريد لآثار التنفيذ**: الكيان يحمل `id` تسلسلياً لكن نموذج النطاق لا يعرضه — بتحديث `ExecutionTraceNode` وإسقاطه من DAO تصبح مفاتيح القائمة مستقرة عبر التحديثات الحية (بدل بادئة الموضع الحالية).
2. **استيراد المجلد بالتدفق (Streaming)**: البديل البنيوي للضغط في الذاكرة هو ZipInputStream يُغذّى مباشرة من اجتياح الشجرة على IO بلا وسيط بايتات — يرفع السقف من «ذاكرة» إلى «قرص» ويصفّر خطر OOM.
3. **لا تقرير انهيارات إطلاقاً في التطبيق**: لا Crashlytics ولا جمع tombstones — لهذا وصلتنا الأعطال كأعراض وصفية بدل تتبعات. (تفصيلها في المقترح الاستراتيجي، بند المعالجة P0-R3.)
4. **تغطية أجهزة حقيقية**: اختبارات e2e الحالية (محاكي API 34) لا تغطي مسار المرفقات من طرف إلى طرف؛ اختبار الانحدار الجديد يسد الفجوة على مستوى Robolectric لكن الجولة القادمة تحتاج مسار SAAS فعلي على جهاز.

## الجزء الثاني — المقترح الاستراتيجي: واجهة تضاهي frontier AI smart workspace

> **المرجع المختار:** Claude (Anthropic) — Artifacts + Canvas + Projects، مع مبدأ «الحالة الصادقة» الذي يتبناه المستودع أصلاً (UNAVAILABLE ≠ HIDDEN). المقترح أدناه **لا يخترع بنى جديدة** — البنية الخلفية الموجودة (Room، RAG محلي، CBR-MDP، سجل العمليات، الأثر المُعرّف) أقوى مما تكشفه الواجهة الحالية؛ المطلوب هو واجهة تُظهر الحقيقة التي يملكها المنطق الخلفي.

### أولاً: تشخيص الفجوة (لماذا الواجهة لا تعكس قدرات التطبيق؟)

التطبيق يمتلك خلفياً: محادثات دائمة قابلة للبحث والتصدير وإعادة التسمية، أثر مُعرّف بنسخ وتراجع، نافذة سياق مقاسة فعلياً، معرض قرار اقتصادي (CBR-MDP)، تنفيذ مُدار بموافقات، رادار قدرات، RAG محلي بنموذج ONNX، نقل ملفات ذري بحدود وتدقيق. بينما الواجهة تقدم هذه كـ«قوائم إدارية» متفرقة (شاشات مستقلة تحت تبويبات) بدل تقديمها كقدرات **داخل** جريان المحادثة نفسه. الفجوة ليست غياب ميزات بل **غياب لحظة الاستخدام**: القدرة تظهر في مكان، والحاجة إليها تقع في مكان آخر.

ثلاث فجوات بنيوية حاكمة:

1. **مركزية الشاشة بدل مركزية المحادثة**: البنية التحتية للأثر والسياق والقرار موجودة لكنها موزعة على وجهات منفصلة؛ لا يوجد «مكان واحد» يجمع جريان العمل الحي.
2. **غياب طبقة الكشف التدريجي الموحدة**: حتى بعد توحيد زر + في هذا الإسعاف، لا يزال استدعاء الأدوات/المهارات/الوكلاء يتطلب فتح لوحات منفصلة بدل إيماءات مضمّنة (slash/سحب/إفلات).
3. **لا حلقة ملاحظات للانهيار**: بلا تقرير انهيارات، كل عطل يصل كوصف لفظي — أغلى ما يمكن في دورة الإصلاح وأبطؤه.

### ثانياً: مبادئ التصميم الحاكمة (مستلهمة من Claude، ملائمة لهوية التطبيق)

| المبدأ | المعنى العملي |
|---|---|
| **المحادثة أولاً، القدرة عند الطلب** | كل قدرة تُستدعى من داخل خانة الإدخال أو من رسالة في الخط الزمني — لا بمغادرة المحادثة إلى شاشة إدارية |
| **حالة صادقة دائماً** | توسيع قاعدة UNAVAILABLE ≠ HIDDEN القائمة: كل عنصر معطّل يحمل سببه الحقيقي، وكل رقم معروض مقاس لا مخترع |
| **سطح واحد لمفهوم واحد** | لا مدخلين لنفس الفعل (طبّقناه إسعافياً على المرفقات — يعمّم على كل المفاهيم) |
| **المخرجات مواطن من الدرجة الأولى** | كل إجابة قابلة للتحويل لأثر يُفتح بجانب المحادثة (Canvas) بدل أن يُدفن في النص |
| **السياق مرئي وقابل للإدارة** | نافذة السياق، المرفقات، والمعرفة المسترجعة — أرقام ظاهرة وأزرار تحكم فعلية لا مؤشرات جمالية |

### ثالثاً: خارطة الطريق المرحلية

#### المرحلة P0 — «الاستقرار قبل الجمال» (أسبوع – أسبوعان)

الهدف: صفر انهيار + حلقة ملاحظات. بنودها:

- **P0-R1 تقرير الانهيارات**: دمج Crashlytics (أو خيار محلي صادق: كتابة tombstone محلي مع عرضها في شاشة System Health الموجودة أصلاً) — شرط القبول: أي انهيار مستقبلي يصل بتتبع كامل بدل وصف لفظي.
- **P0-R2 إغلاق الديون الفنية الأربعة** الموثقة أعلاه (معرف صف التتبع، الاستيراد بالتدفق، تغطية e2e للمرفقات على جهاز فعلي).
- **P0-R3 حراسة ANR**: جدولة `StrictMode` في بناء debug مع `penaltyLog` (لا penaltyDeath في الإنتاج) + اختبار وحدة يفشل إذا لمس مسار حرج الخيط الرئيسي القرص.
- **P0-R4 توحيد مقياس الأداء**: مؤشرات بدء بارد/سخن ووقت فتح الشاشات تُقاس وتُعرض في System Health.

#### المرحلة P1 — «المُحرِّر الحدودي» (2–4 أسابيع)

تحويل خانة الإدخال من حقل نصي إلى سطح قيادة بالكامل:

1. **إيماءات مضمّنة (Slash + @)**: كتابة `/` تفتح قائمة الأوامر المصنفة (نفس كتالوج القدرات الحالي — بلا منطق جديد)، و`@` تفتح: وكلاء، ملفات المشروع، مستندات المعرفة — مع إكمال تلقائي من السجلات الحقيقية. هذه هي النسخة الطبيعية ناضجة من موحّد + الذي ركّبناه إسعافياً.
2. **الإفلات واللصق والكاميرا**: إفلات ملف/مجلد على الشاشة → نفس مسار الاستيراد الحالي (الذي أصبح آمناً)؛ لصق صورة → مسودة مرفق مع سبب عدم التحليل الصادق حتى تفعيل Vision.
3. **معاينة تكلفة السياق قبل الإرسال**: تحت الخانة «هذا السؤال + مرفقاته ≈ N رمزاً من أصل M» — من أرقام الحاكم الاقتصادي **الموجودة أصلاً** (لا تقدير تخميني).
4. **إيقاف/استئناف مرئي**: مؤشر أطوار التنفيذ الحي موجود — يضاف إليه تقدم تفاعلي قابل للتوسيع يعرض خطوات الخطة الفعلية من سجل التنفيذ الدائم.

#### المرحلة P2 — «مساحة العمل الذكية» (4–8 أسابيع)

1. **Canvas جانبي دائم (نمط Claude Artifacts)**: ترقية `SmartArtifactCanvas` الحالي إلى تقسيم قابل للسحب (محادثة | لوحة) على الأجهزة العريضة، مع تحرير مباشر، حفظ نسخة، وتراجع — كلها مدعومة خلفياً بنظام النسخ الموجود.**المخرجات تتحدث**: أي كتلة كود/جدول/مستند في رد المساعد تتحول بلمسة إلى أثر قابل للتحرير.
2. **تفريع الجلسات (Checkpoints)**: «احفظ نقطة» + «ارجع إلى هنا» — تمدد لسجل الجلسات الدائم الحالي؛ التراجع لا يحذف بل يفرّع (نفس نموذج النسخ).
3. **لوحة المشروع (نمط Projects)**: المشروع الحالي (موجود خلفياً بمعزوله الرملي وأثره وRAG) يحصل على وجه: غلاف يجمع آخر المحادثات، الأثر، مستندات المعرفة، وحالة الفهرسة — بلا أي تغيير خلفي.
4. **مركز القرار المرئي**: معرض CBR-MDP موجود — يدمج في المحادثة كبطاقة قابلة للتوسيع فوق كل إجراء وكيل: «لماذا هذا القرار؟ التكلفة؟ البديل المرفوض؟» (البنية توفر كل هذه الحقول أصلاً).

#### المرحلة P3 — «الصقل الحدودي» (مستمر)

- **نظام الحركة والفراغ**: انتقالات 150–250ms لفتح الألواح، ارتداد الأزرار، ومسافات نفسية متسقة (8/16/24dp) — الواجهة الحالية وظيفية لكنها «صامتة» الحركة.
- **طباعة عربية أولاً**: تدقيق خطوط العناوين/النص/الأرقام للأحجام الصغيرة، وأرقام جدولية أحادية العرض في المؤشرات.
- **وضع داكن كامل + ثيم دينامييكي** (Material You) مع اختبارات Roborazzi للوضعين — البنية التحتية للقطات موجودة أصلاً.
- **اختصارات لوحة مفاتيح** للـ tablet/desktop (الاختصارات الموجودة حالياً: Ctrl+Enter للإرسال، Esc للإيقاف — تُوسّع وتُوثق في شاشة مساعدة).

### رابعاً: لماذا هذا الترتيب؟ (منطق المخاطرة)

المرحلة P0 تشتري **الثقة** (لا معنى لبناء واجهة حدودية فوق طاقة انهيار)، P1 تشتري **الإحساس الفوري بالحدودية** بأقل تغيير خلفي (كل بنودها تعاد استخدام بنى قائمة)، P2 هي **القفزة النوعية** التي تحول التطبيق من «شات + شاشات» إلى smart workspace فعلي، وP3 تحافظ على الإحساس بالجودة باستمرار. كل بند في الخارطة معلّق ببنية خلفية **موجودة** — هذا المقترح خطة إظهارٍ للقدرات لا خطة اختراع.

### خامساً: مؤشرات نجاح قابلة للقياس

| المؤشر | الحالي | الهدف بعد المراحل |
|---|---|---|
| انهيارات لكل 100 جلسة | غير مقاسة (لا تقرير) | < 0.1 بعد P0 |
| زمن إرفاق ملف 10MB (حتى ظهور الشريحة) | كان يجمّد الواجهة | < 1.5s بعد الإسعاف، يُقاس ويُعرض بعد P0 |
| استدعاء قدرة دون مغادرة المحادثة | جزئي (بعد توحيد +) | 100% بعد P1 |
| إجابات تُحوَّل إلى أثر قابل للتحرير | يدوي | إيماءة واحدة بعد P2 |
| اختبارات وحدة | 1259 خضراء | تبقى خضراء في كل مرحلة (بند قبول إلزامي) |

## كيفية تطبيق هذا التسليم

```bash
# الخيار أ: تطبيق الرقعة على main مباشرة
git checkout main
git am 000*.patch           # ملفات الرقع المرفقة

# الخيار ب: من الحزمة الجاهزة
git clone ai-v0-hotfix.bundle ai-v0-hotfix
cd ai-v0-hotfix && git checkout hotfix/emergency-ui-crashes
```

ثم الدفع وفتح PR:
```bash
git push origin hotfix/emergency-ui-crashes
```

**التحقق بعد التطبيق:** `./gradlew :app:testDebugUnitTest :app:assembleDebug` (متطابق مع خطوات android.yml — كلها خضراء في هذا التسليم).
